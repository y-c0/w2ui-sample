
w2ui 1.5 で店舗一覧を表示する画面を作りたい。
・一覧の項目は
　店舗ID（登録時はサーバ側で採番する）
　店舗名（テキスト）
　都道府県（マスタから選択）
　editボタン
・通常は編集できないが、editボタンを押すと、その行が編集できる
・行を追加して、新しいデータを追加できる
・グリッド外の登録ボタンを押すことで、サーバに編集行のデータ送信する

c:\my\dev\20260817_w2ui1 に、w2ui 1.5 + jQuery + Express の最小サンプルを作成しました。
API 呼び出し(GET/POST)は実際に起動して動作確認済みです。

構成

package.json — Express依存
server.js — 都道府県マスタ、店舗データ(インメモリ)、GET /api/prefectures、GET /api/stores、POST /api/stores(新規行はサーバ側でID採番)
public/index.html — w2ui 1.5 のグリッド + 行追加/登録ボタン
動作の仕組み

グリッドの列(id/name/pref_code/actions)はすべて w2ui の render 関数でカスタム描画しています。w2ui標準のインライン編集ではなく、editingRecid という変数で「今どの行が編集中か」を管理し、その行だけ <input>/<select> を描画、他の行はテキスト表示にする方式です。
「編集」ボタン → startEdit(recid) でその行だけ編集可能に。「完了」ボタンで編集終了(必須項目チェックあり)。同時に編集できるのは1行のみ。
「＋ 行追加」→ id: null の新規レコードを先頭に追加し、即編集モードに。
「登録」→ 全行を POST /api/stores に送信。サーバは id が null の行にだけ新規採番し、既存行は更新。レスポンスの最新データでグリッドを再描画します。
実行方法


npm install
npm start
その後ブラウザで http://localhost:3000 を開いてください。

なお動作確認時に curl で日本語データを送信した際、ターミナルの文字コード起因で応答が文字化けしましたが({name: "TestStore"} のようなASCIIでは正常)、これはターミナル側の問題で、実際のブラウザの fetch() は UTF-8 で送るため問題ありません。ID自動採番などのロジック自体は正しく動作しています。

追加要件案。
・店舗一覧から、お気に入り店舗を選べる。
・店舗一覧の初期表示時に、お気に入りに設定した店舗だけが表示されるようにする。　それ以外の店舗は、グリッドのリロードか、グリッドの検索機能から検索することで表示される。

このための実装として、
・店舗一覧に「お気に入り」のチェックボックスを追加
・画面側のCookieに、「お気に入り店舗のリスト」を持ち、画面表示時にチェックボックスに反映する
・チェックボックスを編集すると、Cookieに保存される
とするのはどうか？
店舗数が数百件になり、ページングが発生する状況などを考えると、現実的ではないように思う。この案は適切と考えるか？または、別の案はあるか？
まだ実装は行わなくてよい。検討してほしい。



結論から言うと、Cookie案は数百件規模＋ページング前提だと適切ではないと思います。理由は以下の通りです。

Cookie案の問題点

サイズ/送信コストの問題: Cookieは通常4KB程度の上限があり、しかも(pathを絞らない限り)そのドメインへの全リクエスト——グリッドのAPI呼び出しだけでなく画像やJS/CSSの静的リソース取得にまで——毎回付与されます。お気に入りが数十〜百件規模になると無駄な通信コストが無視できなくなります。
「初期表示はお気に入りのみ」とページングの根本的な矛盾: ページングが発生する規模ということは、初期表示で全店舗をサーバから取得してクライアント側でCookieのIDリストによりフィルタする、という方式は成立しません(全件取得自体をやめたいはずなので)。だとすると「お気に入りだけ表示」はサーバ側の検索条件として実装する必要があり、Cookie(クライアントだけが知っている情報)ではサーバがそのフィルタ条件を知りようがありません。
マルチデバイス/マルチブラウザで同期しない: 会社のPCとノートPCで別々のお気に入りになる、ブラウザのCookie削除で消える、といった業務システムとしては望ましくない挙動になります。
代案: お気に入りをサーバ側で永続化する

user_favorites(または store.is_favorite)のようなテーブルをDB側に持ち、「お気に入り店舗一覧」はサーバ側のクエリで絞り込む。
w2uiのグリッドは実は最初から「リモートデータソース(url指定)＋サーバ側ページング/検索」という仕組みを持っているので、初期表示時に favorite=true という検索条件付きでサーバへリクエストし、サーバ側で WHERE id IN (SELECT store_id FROM user_favorites WHERE user_id=?) のように絞り込んだ結果だけを返す、という形が自然です。今回のサンプルは全件をクライアントにロードする方式でしたが、数百件＋ページングを見据えるなら、この機会にリモートグリッド方式へ移行するのが筋が良いと思います。
「リロード」や「検索」で全件・条件検索に切り替えるのも、既存の検索条件を変えるだけなので実装として素直です。


方針が固まりました。まとめると:

設計方針

お気に入りはユーザー単位でDBに保存(例: user_favorites(user_id, store_id))。ただし現状のサンプルには認証機構がないため、実装に進む際は「ユーザーIDをどう取得するか」(セッション/JWT/簡易ログインなど)を先に決める必要があります。
グリッド初期表示は、w2uiのリモートデータソース機能を使い、サーバへ favorite_only=true 相当の検索条件を送って絞り込み結果のみ取得。「リロード」や検索欄のクリアで条件を外せば全件検索に切り替わる、という自然な流れになります。
お気に入りチェックボックスは、行の編集(店舗名・都道府県)とは独立した操作として、クリックした瞬間に POST/DELETE /api/favorites のような専用APIを叩いて即保存。既存の「編集→登録」フローとは分離するので、他の項目を編集中でもお気に入りだけは自由にON/OFFできます。
残っている検討事項(実装前に必要)

ユーザー識別の方法(認証の有無・方式)
グリッドを「全件クライアントロード」から「リモートデータソース(サーバ側ページング/検索)」に切り替える設計変更(現サンプルからの構成変更が必要)
このあたりの方向性で良ければ、認証方式が固まり次第、実装に着手します。

実装したもの

お気に入り チェックボックス列を追加。クリック即座に POST/DELETE /api/favorites/:storeId で保存(店舗名・都道府県の編集フローとは独立)。
グリッドを w2ui のリモートデータソース(url: '/api/stores/search')に切り替え、GET /api/stores/search?request=<JSON> でサーバ側フィルタ/ページング/検索を行う構成に変更(全件クライアントロードは廃止)。
初期表示は favorite_only: true でお気に入り店舗のみをサーバ側で絞り込み。チェックを外すと全12件がページング付きで表示される。
実装中に分かった重要な点

w2ui 1.5.3の実際の通信仕様は、事前の想定(POST + JSON body)と異なり、GET + request=<URLエンコードJSON> クエリパラメータでした。実ソースを確認して修正しています。Spring Boot側で実装する際もこの形式(GETリクエスト、requestパラメータにJSON文字列)に合わせる必要があります。
ブラウザでの実動作をPlaywrightで確認済み: お気に入りのみの初期表示、行編集の1行制限、全件表示時のページング読み込み、いずれも正常動作。ただし全件表示時は「1-12 of 12」のようにスクロールに応じて追加読み込みする挙動(w2uiの pull-more)になっており、ページ番号ボタン式ではありません。実アプリのページングUIがボタン式であれば、そこは調整が必要です。
未対応・要検討事項

ユーザーIDはモックとして固定値(user1)をヘッダで送信しているだけです。Spring Boot側の実認証と繋ぎ込む際は、このヘッダ送信部分を実際のセッション/トークンベースの認証に置き換える必要があります。
